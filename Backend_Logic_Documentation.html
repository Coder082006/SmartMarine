1. Introduction - What is the Backend?

When you use an app like Smart Marine Booking, there are two parts working together:

  1. Frontend (What you see): The screens, buttons, and designs that users interact with
  2. Backend (Behind the scenes): The logic that stores data, processes information, and makes everything work

This document explains the backend logic - the "brain" of the application that handles:

  • Storing user accounts (registration and login)
  • Storing boat schedules
  • Saving bookings/tickets
  • Getting live boat schedules from the cloud
Think of it like this: The frontend is like a restaurant's menu and dining area. The backend is like the kitchen - you don't see it, but it's where all the work happens!

2. Application Architecture Overview

Smart Marine Booking uses two types of storage:

  1. SQLite Database (Local Storage):
    • Stored directly on the user's phone
    • Contains: User accounts, bookings, offline boat data
    • Works without internet
  2. Cloud REST API (Remote Storage):
    • Hosted on Vercel (cloud server)
    • Contains: Live boat schedules
    • Requires internet connection
Key Concept: The app tries to get boat schedules from the cloud first. If the cloud is unavailable, it falls back to the local SQLite database.

3. Database Structure (SQLite)

SQLite is a lightweight database that stores data in a single file on the device. Think of it like an Excel workbook with multiple sheets (tables).

The database file is called: SmartMarine.db

It contains three tables:

Table Name Purpose What it Stores
users Registered accounts User name, email, phone, password
boats Ferry schedules (offline backup) Boat name, route, times, price
bookings User tickets Booking reference, passenger details, trip info
Step-by-Step: How the Database is Created

When a user first opens the app:
1. Android checks if SmartMarine.db exists
2. If not, it creates the database file
3. It creates all three tables
4. The boats table is used for offline backup (the cloud server handles live schedules via web scraping)
5. The database is now ready to use!

4. Users Table - How Registration Works

The users table stores all registered user accounts.

Table Structure

Column Name Data Type Description Example
id INTEGER Unique number for each user (auto-increments) 1, 2, 3...
full_name TEXT User's full name "John Smith"
email TEXT User's email (must be unique) "john@email.com"
phone TEXT Phone number "+255123456789"
password TEXT User's password "secret123"

Registration Process (Step by Step)

When a user fills out the registration form and taps "Register":

Step 1: Validate Input
- Name must be at least 3 characters
- Email must contain @ and . (example: user@email.com)
- Phone must be at least 10 digits
- Password must be at least 6 characters

Step 2: Check if Email Already Exists
- The app asks the database: "Is this email already registered?"
- If YES → Show error: "Email already registered"
- If NO → Continue to Step 3

Step 3: Save to Database
- The app calls: registerUser(name, email, phone, password)
- Database inserts a new row into the users table
- Success! User is now registered

Step 4: Redirect to Login
- User is sent to the login screen to sign in

Login Process (Step by Step)

When a user enters email and password and taps "Login":

Step 1: Validate Input
- Check that email and password fields are not empty

Step 2: Check if Email Exists
- The app calls: emailExists(email)
- If email NOT found → Show: "No account found. Please register first."
- If email found → Continue to Step 3

Step 3: Verify Password
- The app calls: loginUser(email, password)
- Database checks if the password matches the email
- If password WRONG → Show: "Incorrect password."
- If password CORRECT → Continue to Step 4

Step 4: Start Session
- The app saves the user's email in SessionManager
- User is now "logged in"
- Redirect to Home screen
Important Security Note: In this educational project, passwords are stored in plain text. In real-world apps, passwords should always be encrypted (hashed) before storing!

Booking Process (Step by Step)

When a user books a trip:

Step 1: User Selects a Boat
- User browses available boats on the Available screen
- Taps "SELECT" on their preferred boat

Step 2: Payment
- App opens PaymentActivity
- User selects mobile money provider (M-Pesa, etc.)
- User enters phone number
- App simulates payment processing (2.2 seconds)
- Payment succeeds!

Step 3: Create Booking
- App calls: createBooking(...)
- Database generates a reference: "SMB-2026-1005"
- All trip details are saved to the bookings table
- Status is set to "CONFIRMED"

Step 4: Show Ticket + Notify
- User sees their digital ticket with:

  - QR code

Important Rule: A booking is ONLY created AFTER payment succeeds. The app ensures users cannot get a ticket without paying first!

7. Key Database Methods Explained

The DatabaseHelper.java file contains all the methods that interact with the database. Here are the most important ones:

User-Related Methods

Method Name What It Does Returns

emailExists(email) Checks if an email is already registered true or false
loginUser(email, password) Verifies login credentials true (correct) or false (wrong password)
getUserName(email) Gets the user's full name from their email String (full name)

Boat-Related Methods

Method Name What It Does Returns
searchBoats(origin, destination) Finds boats on a specific route List of Boat objects

Booking-Related Methods

Method Name What It Does Returns
createBooking(...) Saves a new booking to database Booking reference (e.g., "SMB-2026-1005")
getBookingsForUser(email) Gets all bookings for a specific user List of Booking objects
Example: How registerUser() Works Internally

public boolean registerUser(String name, String email, String phone, String password) {
  // 1. Open the database
  SQLiteDatabase db = this.getWritableDatabase();

  // 2. Create a container for the data
  ContentValues values = new ContentValues();
  values.put("full_name", name);
  values.put("email", email.toLowerCase());
  values.put("phone", phone);
  values.put("password", password);

  // 3. Try to insert into the "users" table
  long result = db.insert("users", null, values);

  // 4. Check if it worked
  if (result == -1) {
    return false; // Failed (email already exists)
  } else {
    return true; // Success!
  }
}

8. Session Management - Keeping Users Logged In

The SessionManager.java uses Android's SharedPreferences to remember who is logged in.

Think of SessionManager like this:
When you check into a hotel, they give you a room key. The key doesn't store your luggage - it just lets you access your room. Similarly, SessionManager stores a "key" (the email) that lets the app know who you are. Your actual data is in the database!

Session Methods

Method Name What It Does
login(email) Saves the email as "logged in"
logout() Removes the saved email (logs out)
getEmail() Returns the logged-in user's email
isLoggedIn() Checks if someone is logged in (true/false)

How Session Works

Login Flow:
1. User logs in successfully
2. App calls: session.login("john@email.com")
3. SessionManager saves "john@email.com" in SharedPreferences
4. Now the app knows who the user is!

Using the Session:
- To get bookings: session.getEmail() → "john@email.com"
- Database then loads bookings WHERE user_email = "john@email.com"

Logout Flow:
1. User taps Logout
2. App calls: session.logout()
3. SessionManager removes the saved email
4. App returns to Login screen

9. Cloud REST API (Node.js Backend)

The cloud API is a separate server running on Vercel that provides live boat schedules. It scrapes ferry departure times from zanzibarferries.com on startup and refreshes every 30 minutes.

What is a REST API?

REST API is like a waiter in a restaurant:

  • You (the app) tell the waiter what you want
  • The waiter goes to the kitchen (server/database)
  • The waiter brings back what you ordered

API Endpoints

Endpoint Method What It Does Example Request
/ GET Health check - Is the server running? Visit the URL
/api/boats GET Get boats for a specific route /api/boats?from=Dar es Salaam&to=Zanzibar
/api/bookings POST Create a new booking Send booking details as JSON
/api/bookings GET Get all bookings for a user /api/bookings?email=john@email.com

How the App Talks to the Cloud

ApiClient.java handles all communication with the cloud.

Example: Searching for Boats
1. User searches "Dar es Salaam to Zanzibar"
2. App calls: ApiClient.searchBoats("Dar es Salaam", "Zanzibar", callback)
3. ApiClient sends GET request to: https://smart-marine.vercel.app/api/boats?from=Dar+es+Salaam&to=Zanzibar
4. Server responds with JSON list of boats
5. ApiClient converts JSON to Boat objects
6. App displays the boats to the user
Important: The cloud API is the primary source for boat schedules. The local SQLite boats table is only used as a backup if the cloud is unavailable!

Cloud Fallback Logic

What Happens When You Search:

Scenario 1: Cloud is Available
- App asks cloud for boats
- Cloud responds with list of boats
- App displays the boats

Scenario 2: Cloud is Unavailable
- App asks cloud for boats
- No response (server is down or no internet)
- App shows error: "Couldn't reach the schedule server"
- App does NOT fall back to local data (by design)

Scenario 3: No Cloud Configured
- App checks if cloud URL is set
- If not configured → Uses local SQLite database
- Searches the boats table locally

10. Web Scraper - Live Schedule Fetching

The server includes a web scraper that fetches real ferry schedules from zanzibarferries.com. This means the app shows actual departure times from the ferry operator's website, not just hardcoded data.

How the Scraper Works

Step-by-Step: What Happens When the Server Starts

Step 1: Fetch the Website
- Server sends an HTTP request to zanzibarferries.com
- Waits up to 15 seconds for a response
- If the site is down → Falls back to static data

Step 2: Parse the HTML
- Uses cheerio (a library that parses HTML like jQuery)
- Finds all <table> elements on the page
- Extracts rows with ferry names and departure times

Step 3: Determine Route Direction
- Looks at headings before each table to figure out direction
- "Zanzibar to Dar" → origin = Zanzibar, destination = Dar es Salaam
- "Dar to Zanzibar" → origin = Dar es Salaam, destination = Zanzibar

Step 4: Add Static Routes
- Appends Pemba routes (ZanFast Ferry) - not on the website
- Appends Mafia routes (Kivukoni Ferry) - not on the website

Step 5: Store in Memory
- All 12 boats are stored in the server's memory
- Ready to serve to the Android app via API

Scraper File: schedule-scraper.js

Component What It Does
scrapeSchedules() Main function - fetches and parses the website, returns array of boats
findDirectionHint() Determines if a table is Dar→Zanzibar or Zanzibar→Dar
estimateArrival() Calculates arrival time (~1h 45min after departure)
FALLBACK_BOATS Static backup data used if the website is unreachable
STATIC_ROUTES Pemba and Mafia routes (not available on zanzibarferries.com)

Refresh Schedule

Auto-Refresh: The scraper runs automatically:
- On server startup: Fetches fresh data immediately
- Every 30 minutes: Re-fetches to get updated schedules
- On each API request: If data is older than 30 minutes, refreshes on-demand

Route Summary

Route Data Source Frequency
Dar es Salaam ↔ Zanzibar Scraped live from zanzibarferries.com 4 ferries each direction
Zanzibar ↔ Pemba Static (ZanFast Ferry) 6 sailings/week
Dar es Salaam ↔ Mafia Static (Kivukoni Ferry) Irregular schedule
Total: 12 boats across 6 routes
8 routes are scraped live, 4 routes use static data because no public schedule website exists for Pemba and Mafia ferries.

11. How Data Flows Through the App

Let's follow a complete user journey to see how all the backend pieces work together.

Complete Booking Flow

User Journey: John books a trip from Dar es Salaam to Zanzibar

1. Registration
- John fills out registration form
- App validates input (name ≥ 3 chars, email valid, etc.)
- App checks if email exists → No

- John is redirected to Login screen

2. Login
- John enters email and password
- App checks: emailExists("john@email.com") → True
- App checks: loginUser("john@email.com", "pass123") → True
- App calls: session.login("john@email.com")
- SessionManager saves the email
- John is on the Home screen

3. Search for Boats
- John taps "Search Boats"
- GPS detects he's near Dar es Salaam (auto-fills "From")
- John enters "Zanzibar" as destination
- John picks a travel date
- App sends request to cloud API
- Cloud responds with available boats

4. Select Boat
- John sees "Azam Marine - 08:00 - TZS 35,000"
- John taps "SELECT"
- App opens PaymentActivity

5. Payment
- John selects "M-Pesa"
- John enters his phone number
- John taps "PAY"
- App simulates payment (2.2 seconds)
- Payment success!

6. Create Booking
- App calls: createBooking(...)
- Database generates reference: "SMB-2026-1005"
- Booking saved to database with status "CONFIRMED"
- John sees his digital ticket with QR code

7. View Booking Later
- John goes to "My Bookings"
- App calls: getBookingsForUser("john@email.com")
- Database returns John's bookings
- John sees his confirmed ticket

Data Flow Diagram

Registration:
User Input → Validate → Database (INSERT) → Success

Login:
User Input → Check Email Exists → Check Password → Create Session → Home Screen

Search Boats:
User Input → Cloud API (GET) → Server checks in-memory boats (scraped) → Return filtered list → Display to User

Book Trip:
Select Boat → Payment → Create Booking (INSERT) → Generate Ticket (QR + PDF) → Notify + Email

12. Summary

Key Takeaways

  1. Database is the Heart: SQLite stores all user data, bookings, and offline boat schedules
  2. Two Types of Data:
    • Local (SQLite): Users, Bookings, Offline Boats
    • Cloud (REST API): Live Boat Schedules scraped from zanzibarferries.com
  3. Live Scraping: Dar↔Zanzibar schedules are fetched from the real ferry website
  4. Session = Login State: SessionManager just remembers who is logged in (not the actual data)
  5. Cloud First, Then Local: The app tries to get boats from the cloud first
  6. Booking Requires Payment: Users cannot get a ticket without successful payment
  7. Digital Tickets: Each booking generates a QR code and PDF ticket, auto-emailed to the user
  8. Push Notifications: Users receive an on-device notification when their booking is confirmed
  9. Reference Numbers: Each booking gets a unique reference like "SMB-2026-1005"
